# 簡化技術中文（依 ASD-STE100 精神調整）

ASD-STE100（Simplified Technical English）是航太與國防產業建立的控制語言標準，目的是避免維修技師誤讀英文操作指示：消除一詞多義的字，也消除可能有多種解讀方式的句子結構。

**這套標準本身只涵蓋英文**，官方並沒有發布對應的「簡化技術中文」標準。本 skill 借用它背後的核心原則——**讓一個沒有機會回頭發問的讀者，不可能誤讀**——重新設計成一套適用於**繁體中文**的改寫規則，處理中文特有的歧義來源：省略主詞、「的」的巢狀修飾、「了／過／著」造成的時序不清、代名詞指代不明等。這不是官方標準的翻譯本，而是同一原則的中文衍生版本。

## 何時使用本 Skill

- 文件、說明、錯誤訊息、agent 之間的指令讀起來語意模糊、句子太長，或有多種解讀可能。
- 文字會被另一個 agent、翻譯流程，或非母語讀者消化，而誤解會造成實際代價（操作錯誤、流程卡住、安全疑慮）。
- 你正在撰寫中文的 prompt、system message 或工具說明，希望先消除歧義再讓模型讀取。
- 你想要一份**改寫前／改寫後**對照表，清楚標示違反了哪一條規則、又是如何修正的。

**涵蓋的技術文件類型（觸發情境）：**
- Code review 留言、PR／MR 說明、commit message 的中文描述。
- OpenSpec 文件：`proposal.md`（提案）、`spec.md`（規格）、`tasks.md`（任務拆解）、`design.md`（設計說明）等。
- README、架構設計文件、RFC、ADR（架構決策紀錄）。
- API 文件、SOP、Runbook、教學／操作說明。
- 錯誤訊息、日誌訊息、工具描述、agent 之間的指令。

只要輸出的中文屬於以上任一類型、且會被人或另一個系統依字面意思解讀並據以行動，就適用本 skill；純粹閒聊或內部草稿式的中文不必套用。

本 skill 不適用於文學、行銷或需要語氣與韻味的文案——這類文字的重點正是細膩與感染力，套用本規則會把它寫死、寫平。

## 核心改寫規則（依中文特性調整）

| 規則 | 該做 | 不該做 |
|---|---|---|
| 一詞一義 | 同一動作全文固定用同一個詞（例如全篇統一用「檢查」，不要在「檢查／確認／核實」之間切換） | 對同一概念在不同段落換用不同近義詞，讓讀者猜測是否為同一件事 |
| 主動語態優先 | 「系統刪除該檔案。」 | 「該檔案被系統刪除。」——除非動作執行者確實未知或無關緊要 |
| 明確主詞，不隨意省略 | 「使用者送出請求後，伺服器會驗證權杖。」 | 「送出請求後，會驗證權杖。」——沒說清楚是誰驗證、驗證誰的權杖 |
| 明確時序，避免「了／過／著」造成的歧義 | 「工作完成後，系統會讀取結果。」 | 「工作完成了系統讀取結果。」——動作先後與因果關係不清 |
| 一句一指令 | 「開啟檔案。讀取第 3 行。」 | 「開啟檔案並讀取第 3 行，然後檢查是否相符。」 |
| 句子長度 | 指令句／程序句 ≤ 40 字，描述句 ≤ 50 字（中文資訊密度較高，字數上限略低於英文的字數上限） | 用逗號一路連下去的長句 |
| 避免「的」多層巢狀修飾 | 「用來設定佇列優先順序的處理器」 | 「agent 任務佇列優先順序處理器」——多層名詞堆疊，修飾對象不明 |
| 代名詞指代明確 | 明確寫出「該檔案」「此設定」，而非只用「它」「這個」 | 連續使用「它」「這個」「那個」，讓讀者要往回找才知道指什麼 |
| 段落限制 | 一段一主題，≤ 6 句 | 一段夾雜多個主題 |
| 用清單表示流程 | 3 個以上步驟或條件，用編號或條列清單呈現 | 把一連串步驟塞進一句散文式的句子裡 |
| 數字與範圍明確 | 「等待逾時 30 秒後重試。」 | 「等待一段時間後再重試。」——安全或流程關鍵資訊不該用模糊字眼 |
| 術語定義與統一 | 專有名詞第一次出現時定義一次，之後全文統一用字 | 使用術語卻從不定義，或同一術語在不同段落有不同寫法（含繁簡混用） |
| 用字與標點 | 使用繁體中文標準用字（依台灣用語習慣）與全形標點（，。；：） | 逐字直譯英文語序、混用簡體字或半形標點 |

## 處理流程

1. 先通讀一次輸入文字以理解其意義——在確定改寫後仍須傳達的內容之前，不要動手改寫。
2. 逐句檢視，標出每一處違反規則的地方（用字歧義、被動語態、省略主詞、時序不清、代名詞不明、句長、名詞堆疊）。
3. 針對每個被標記的句子進行改寫，修正違規之處，同時完整保留原意。如果某個改寫會讓必要的精確度流失（安全條件、範圍限定詞、數字），就保留較長的說法並加以標記，而不是悄悄簡化掉。
4. 產出改寫前／改寫後對照表（見「輸出格式」）。
5. 如果輸入文字已經符合規範，就明確說明——不要對已合規的文字硬套用變更。

## 輸出格式

```markdown
| 違反的規則 | 原文 | 簡化後 |
|---|---|---|
| 省略主詞 | 「送出請求後，會驗證權杖。」 | 「使用者送出請求後，伺服器會驗證權杖。」 |
| 名詞堆疊 | 「agent 任務佇列優先順序處理器」 | 「用來設定任務佇列優先順序的處理器」 |
```

在對照表之後，附上一行說明：哪些地方你刻意**沒有**簡化，以及原因（通常是：簡化會流失必要的精確度）。

## 範圍界定

**會做：**
- 將意義模糊、冗長或有歧義的繁體中文，改寫成短句、單一意義、主動語態、主詞明確的句子。
- 在改寫句子之前，先標出它確切違反了哪一條規則。
- 保留原文中的每一項事實、條件與範圍限定詞。
- 對於必須保留的領域術語，提供一行詞彙表建議，並統一全文用字。
- 預設使用台灣繁體中文用語與全形標點；若上下文明確使用其他地區用語習慣，會依上下文調整並註明。

**不會做：**
- 聲稱這是官方或經認證的「簡化技術中文」標準——目前沒有對應 ASD-STE100 的官方中文標準，本 skill 只是依同一原則做的衍生工具。
- 簡化文學、行銷或需要語氣與細膩度的文案。
- 為了縮短句子而悄悄刪去安全條件、例外情況或範圍限定詞——遇到這種取捨會直接標記出來，而不是默默處理。
- 把中文機械式地套用英文語序或逐字直譯規則；規則會依中文語法特性調整，而非照搬英文版逐條翻譯。
