# ASD-STE100 規則類別與中文轉換對照

本檔案說明 ASD-STE100（Simplified Technical English）的原始規則類別，以及本 skill 如何把每一類規則轉換成適用於繁體中文的版本。它是規則*類別*的說明，不是官方標準文字的翻譯，也不構成任何官方認證。

## ASD-STE100 是什麼

ASD-STE100 是一套控制式自然語言，1986 年首次發布（當時文件編號為 AECMA Document PSC-85-16598），由現在的 ASD（歐洲航太與國防工業協會）建立。它是應歐洲航空公司要求而生——當時許多維修人員的母語不是英文，需要一套不會被誤讀的維修文件，因為飛機上的操作指示一旦被誤讀，是會出人命的。這套標準由 Simplified Technical English Maintenance Group（STEMG）維護，自第 6 版（2013 年）起免費開放下載，目前最新為第 9 版（2025 年 1 月）。

**中文沒有對應的官方標準。** 中文世界中較接近的概念是台灣與中國大陸政府單位陸續推動的「簡明用語」「淺白語言」（Plain Language）文件寫作原則，但這些多半是行政文書的可讀性指引，並不是像 ASD-STE100 這樣有完整字典與 53 條規則的控制語言標準。本 skill 因此是原創的衍生設計：借用 ASD-STE100 背後的方法論（消除一詞多義與句構多義），重新對應到中文的實際語法現象。

## 規則類別與中文對應

**用字選擇（英文原則：一詞一義、一詞一詞性）**
中文的對應問題不是詞性混用（中文詞性彈性本來就大），而是：
- 同一動作在全文中使用不同近義詞，讓讀者無法判斷是否為同一件事（如「檢查」「確認」「核實」交替使用）。
- 一個字在同一份文件裡身兼多種意義而未加區分（例如「執行」既可指「執行程式」也可指「執行任務」時，若上下文不夠明確就會混淆）。

**動詞形式與時態（英文原則：只用簡單時態，禁用完成式）**
中文動詞不因時態變化字形，對應問題轉換為：
- 「了／過／著」等時貌助詞使用不一致，造成動作是否完成、是否持續的判斷困難。
- 缺少明確時間詞（之前、之後、目前、屆時）時，句子內多個動作的先後順序容易混淆。
- 建議：優先使用明確的時間副詞與連接詞（先…再…、…之後…）取代僅靠助詞暗示順序。

**語態（英文原則：程序文字必須主動語態）**
- 中文「被」字句在技術文件中同樣會模糊動作執行者，尤其當「被」字句省略施動者時（如「檔案被刪除」，未說明是誰刪除、為何刪除）。
- 對應規則：程序性、指令性文字一律主動語態，並明確寫出動作執行者；描述性文字若執行者確實不重要或未知，才允許被動句式。

**句子結構（英文原則：一句一指令、有長度上限、不省略句子成分、名詞群組上限 3 字）**
- 中文最大的結構性歧義來源是**省略主詞**（中文口語與書面語都習慣省略，但技術文件中省略主詞常導致「誰做了什麼」不明確）與**「的」的多層巢狀修飾**（多個「的」疊加時，修飾對象容易誤判）。
- 句長上限依中文資訊密度略低於英文對應版本：指令句／程序句建議 ≤ 40 字，描述句 ≤ 50 字（英文版對應為 ≤20 / ≤25 個英文字，但中文一字承載的資訊量較高，故字數上限相應調降，而非直接套用英文的字數）。
- 名詞堆疊：中文同樣會出現「agent 任務佇列優先順序處理器」這類疊字修飾，建議拆解為「用來設定任務佇列優先順序的處理器」等結構清楚的說法。

**段落與文件結構（英文原則：一段一主題，段落與清單長度限制）**
- 直接沿用：一段一主題、段落不超過約 6 句；3 個以上的步驟或條件一律改用編號或條列清單，不要埋在一段散文裡。

**安全指示（英文原則：安全指令要有清楚的命令或條件開頭，不能埋在句子中間）**
- 直接沿用：安全或風險相關的指示，句首就要是明確的命令或條件（例如「注意：」「若發生逾時，請先確認…」），不要放在句子後半段才提及。

## 本 skill 為何把 STE 精神轉用到繁體中文

STE 的設計初衷，是服務一個沒有機會回頭發問的讀者——在機坪上依手冊作業的技師，手邊沒有作者可以打電話詢問。AI agent 在解析另一個 agent 的輸出、工具描述或系統訊息時，處境完全相同：沒有旁路管道可以確認「這句被動句究竟是呼叫方做了 X，還是被呼叫方做了 X？」保護飛機維修技師不被誤讀扭力規格所設計的同一套規則精神，經過語言特性的轉換後，同樣能保護下游 agent 不被誤讀指令——不論原文是英文還是繁體中文。
