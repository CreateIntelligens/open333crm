## Context

粉絲活動的寫入都是「先讀、再寫」：先查有沒有作答、先讀餘額、先讀未中獎名單、先讀活動狀態，再寫入。PostgreSQL 預設的隔離等級是 read committed，同時進來的兩個交易都讀得到寫入之前的資料，所以都會通過檢查。

## Goals / Non-Goals

**Goals:**

- 同時操作時，`portal-activity` 主規格的每個 Requirement 都成立。
- `contact-management` 的積分 Scenario 在同時調整積分時也成立。

**Non-Goals:**

- 不修 PORTAL-01、PORTAL-02（`docs/ref/system/AUDIT.md`）。粉絲端的路由仍把錯誤一律回 400。
- 不改積分帳本的資料結構：餘額仍取 `createdAt` 最新一筆的 `balance`。

## Decisions

### 1. 每一種寫入用哪一把鎖

| 寫入 | 鎖 | 為什麼選這把鎖 |
| --- | --- | --- |
| 送出不允許重複參加的活動 | advisory lock，鍵是 `portal-submit:<活動>:<聯絡人>` | 只讓同一位粉絲的送出排隊。鎖活動列的話，所有粉絲的送出都要排隊 |
| 寫入積分帳本 | advisory lock，鍵是 `point-ledger:<聯絡人>` | 帳本沒有一列可以鎖。鎖聯絡人列會擋住聯絡人的其他修改 |
| 抽獎、編輯、刪除、狀態轉換 | 活動列的 `SELECT … FOR UPDATE` | 狀態就在這一列。等鎖期間活動被刪除時，`FOR UPDATE` 回 0 列，系統回找不到 |

資料庫沒有唯一限制可以擋重複作答：活動是否允許重複參加，存在 `settings` 的 JSON 裡，partial unique index 無法依它判斷。

### 2. 鎖的順序

- 送出：作答鎖 → 帳本鎖。
- 合併：聯絡人列鎖（依 id 排序，`contact-merge.service.ts` 原本就有）→ 雙方的帳本鎖。
- 解除合併：合併紀錄的條件更新 → 雙方的帳本鎖。
- 後台調整積分：只有帳本鎖。

同時鎖多位聯絡人的帳本時，`lockPointLedgers()` 依 id 排序取得，所以「A 轉 B」與「B 轉 A」同時進行時不會死結。沒有任何寫入先拿帳本鎖、再拿作答鎖或聯絡人列鎖。

### 3. 帳本的寫入時間

同時寫入的問題用鎖解決之後，兩筆仍可能在同一毫秒寫入（`createdAt` 是 `TIMESTAMP(3)`）。這時「取最新一筆」不確定，餘額可能取到前一筆。`addPointTransaction()` 在鎖住之後，把寫入時間設成「現在」與「最新一筆＋1 毫秒」中較晚的一個。合併原本就用同樣的方法讓轉出與轉入排在雙方既有交易之後。

## Risks / Trade-offs

- **送出與結束活動同時進行時，送出可能成功。** 送出時不鎖活動列。送出讀到活動已發布之後，結束才 commit，所以會多一筆剛好在結束時送出的作答。這要毫秒等級的巧合，也不會產生錯誤資料，因此不修。要修的話，送出時以 `FOR SHARE` 鎖住活動列，結束就要等進行中的送出 commit。
- **同一位聯絡人的積分寫入依序執行。** 同一位聯絡人同時有大量寫入時（例如同時參加很多活動），後面的寫入要排隊。每筆寫入只有兩個查詢，所以影響很小。
