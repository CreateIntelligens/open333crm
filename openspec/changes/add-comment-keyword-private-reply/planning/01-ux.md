# 01 — UI/UX 規劃：留言關鍵字自動私訊

> 範圍：後台 `apps/web` 的資訊架構、頁面、文案、狀態與權限差異，以及 UI 需要的 API。
> 不含資料庫與 worker 的實作設計（見架構規劃）。
> 參照的現有畫面：`apps/web/src/app/dashboard/line/keyword-replies/page.tsx`、
> `apps/web/src/components/line/keyword-reply/KeywordReplyEditDialog.tsx`、
> `apps/web/src/app/dashboard/line/follow-gift/page.tsx`、`apps/web/src/components/layout/Sidebar.tsx`、
> `apps/web/src/components/settings/ChannelManagement.tsx`、`apps/web/src/app/dashboard/automation/[ruleId]`。
> 設計語言一律沿用這些頁面：`Topbar`、`max-w-6xl` 主欄、白底 `rounded-lg border` 卡片、「怎麼用？」說明區塊、
> `rounded-full` 狀態 pill（`success-subtle`／`warning-subtle`／`destructive-subtle`／`muted`／`primary-subtle`）、
> 關鍵字 chip（`border-primary-border bg-primary-subtle text-primary`）、`components/ui/tabs.tsx`。
> 不放 emoji，成功訊息不加勾勾符號。範例中的人名、貼文內容都是虛構的。

## 0. 從現有程式讀到、會影響 UX 的事實

| 事實 | 出處 | 對本功能的影響 |
| ---- | ---- | ---- |
| 側欄「渠道」群組整組用 `perm: 'richmenu.manage'` 擋住，子項目「關鍵字回覆」也跟著被擋 | `Sidebar.tsx` | 新頁面若放在「渠道」底下，沒有 `richmenu.manage` 的人即使有 `comment_reply.view` 也看不到入口。見 §2 |
| 素材庫只有 `line`、`fb` 兩種 channelType，Instagram 沒有素材 | `useKeywordReplies.ts` 的 `KEYWORD_REPLY_CHANNELS` | IG 規則的私訊內容只能是文字。UI 要像關鍵字回覆頁一樣明講「Instagram 目前沒有素材」 |
| 關鍵字回覆的比對是「包含、不分大小寫」，有任一／全部兩種模式，UI 用 chip + Enter 加入 | `KeywordReplyEditDialog.tsx` | 直接沿用元件與用詞，使用者不必學兩套 |
| 關鍵字回覆的素材若含顧客專屬券連結會被擋下（`COUPON_URL_IN_RULE_MESSAGE`） | 同上 | 留言私訊送出時通常還沒有聯絡人，同樣要擋，沿用同一則訊息 |
| 渠道可見性有三種存取層級 `read_only`／`reply_only`／`full`，`channel.view_all` 看全部 | `apps/api/src/services/channel-visibility.ts` | 規則與紀錄要依渠道過濾；能不能改規則要看該渠道的層級。見 §8 |
| FB 渠道有權杖狀態 `GET /channels/:id/status` 的 `tokenStatus.warning` | `ChannelManagement.tsx` | 前置條件檢查可沿用同一支 API 擴充，見 §5 |
| 收件匣已有系統訊息樣式（`senderType === 'SYSTEM'`） | `components/inbox/MessageBubble.tsx` | 「來自留言」的脈絡用系統訊息呈現，不必發明新元件。見 §7 |
| 列表類 hook 多用 SWR `refreshInterval: 30000` | `useAutomation.ts`、`useCases.ts` | 觸發紀錄沿用 30 秒輪詢，見 §11 |

## 1. 使用者與情境

### 角色

| 角色 | 目標 | 常做的事 | 對應權限 |
| ---- | ---- | ---- | ---- |
| 小編（社群經營） | 發文前把自動私訊設好，活動期間不必守著留言區 | 建規則、指定貼文、測試、看有沒有送出 | `comment_reply.manage` |
| 行銷（活動負責人） | 留言轉私訊的成效、名單 | 看觸發紀錄與數量、匯出 | `comment_reply.view` |
| 客服主管 | 處理客訴「我留言了怎麼沒收到」、確認接手的對話有脈絡 | 搜尋觸發紀錄、看失敗原因、從紀錄跳到收件匣 | `comment_reply.view` + `inbox.view` |
| 分店店員（渠道受限） | 只管自己分店的粉專 | 只看到被授權渠道的規則與紀錄 | 依渠道可見性 |

### 情境

1. **活動貼文「留 +1 送券」（一般零售品牌，FB）**
   某手搖飲品牌發「留言 +1 抽第二杯半價」。小編建規則：渠道＝品牌粉專，關鍵字 `+1`、`加一`（任一），貼文範圍＝這一篇，
   私訊內容＝素材「第二杯半價說明」（文字＋按鈕），公開回覆＝「已私訊給你囉，請到收件匣查看」。
   痛點：留言量大，同一個人會留好幾次；7 天後還有人留言。UX 要點：「同一位留言者只私訊一次」預設開啟；
   過期的留言在紀錄中標「已過期」，不是「失敗」。

2. **留「價格」私訊價目表（創造智能，FB＋IG）**
   創造智能在 FB 與 IG 都貼「AI 客服方案介紹」，常有人留「價格」「多少錢」「報價」。行銷建兩條規則（FB 一條、IG 一條），
   關鍵字任一命中，貼文範圍＝全部貼文。FB 私訊用素材「方案價目表」，IG 只能用文字（附官網連結）。
   痛點：不想公開回覆價格，只要私訊；全部貼文都適用。UX 要點：不設公開回覆；「全部貼文」要明講包含以後的新貼文。

3. **指定某幾篇貼文（一般零售品牌，IG）**
   服飾品牌一週發三篇新品 Reels，留「尺寸」就私訊尺寸表。小編從「最近貼文」清單勾三篇，不用找 ID。
   痛點：IG 網址裡的 shortcode 不是 media ID，使用者無從得知 ID。UX 要點：以「從最近貼文挑選」為主，貼網址為輔。

4. **兩段式領券（創造智能示範給客戶看的玩法）**
   留言只能私訊一次，且送出時還沒有對話與聯絡人，所以不適合直接發顧客專屬券。做法：私訊內容寫「回覆『領券』即可領取」，
   顧客回覆後進入既有的「關鍵字回覆」流程發券（此時已有對話、24 小時視窗也開了）。UX 要點：規則編輯頁的說明直接教這個玩法，
   並連到「關鍵字回覆」頁。

5. **客訴排查（客服主管）**
   顧客私訊抱怨「我留言了沒收到」。主管在觸發紀錄用顧客名稱搜尋：找到一筆「已過期：留言超過 7 天」或「未命中規則」
   （沒有紀錄），能直接回答顧客，不必找工程師。UX 要點：紀錄可依留言者名稱、留言內容搜尋；沒有紀錄時頁面要提示
   「沒有紀錄代表留言沒有命中任何啟用中的規則，或系統沒有收到這則留言」，並提供「規則試算」。

## 2. 資訊架構

### 放在側欄哪裡

建議放在「行銷與渠道」群組的第一層，與「行銷」「渠道」「粉絲活動」「短連結」並列：

```
行銷與渠道
├─ 行銷 ▸
├─ 渠道 ▸            （LINE Rich Menu、關鍵字回覆、LINE 加好友禮、LINE 快速回覆）
├─ 留言自動私訊       ← 新增，perm: comment_reply.view，icon: MessagesSquare
├─ 粉絲活動 ▸
└─ 短連結 ▸
```

理由：

- 概念上它和「關鍵字回覆」是兄弟功能，應該靠近。但「渠道」群組整組被 `richmenu.manage` 擋住（§0），放進去會讓只有
  `comment_reply.view` 的行銷看不到入口。改 `渠道` 群組的權限邏輯會影響既有功能，不屬於本 change。
- 它是「獲客」工具（把公開互動轉成私訊名單），使用者會在「行銷與渠道」找它，而不是「自動化與知識」。
- 單一頁面（內含分頁），不需要子選單，第一層一個連結即可。

後續可另開 change 把「渠道」群組的權限改到子項目上（像「報表」群組那樣），屆時再把本頁移進「渠道」。

### 頁面名稱與 URL

| 項目 | 建議 | 理由 |
| ---- | ---- | ---- |
| 側欄與頁面標題 | **留言自動私訊** | 說出「觸發點（留言）」與「結果（私訊）」。「留言關鍵字回覆」容易被誤會成「自動公開回覆留言」 |
| Topbar title | 渠道 | 與關鍵字回覆頁一致 |
| 列表 URL | `/dashboard/comment-replies` | 不是 LINE 功能，不放 `/line/` 底下；與既有 `/dashboard/line/keyword-replies` 的歷史包袱無關 |
| 規則編輯 | `/dashboard/comment-replies/new`、`/dashboard/comment-replies/[ruleId]` | 理由見 §3「對話框或獨立頁」 |
| 觸發紀錄 | `/dashboard/comment-replies?tab=logs`（可帶 `ruleId`、`status` 等查詢參數） | 分頁狀態放 URL，從規則列表「查看紀錄」、從收件匣系統訊息都能直接連結 |

### 分頁

`components/ui/tabs.tsx`，兩個分頁：

1. **規則**（預設）
2. **觸發紀錄**（分頁標籤旁顯示近 24 小時「失敗」筆數，例如「觸發紀錄（3 筆失敗）」，有失敗才顯示，`text-destructive`）

### 讓使用者分清楚「關鍵字回覆」「自動化」「留言自動私訊」

在頁首「怎麼用？」區塊放一張三列對照（純文字表格，不用圖示）：

| 顧客做了什麼 | 用哪個功能 | 系統怎麼回 |
| ---- | ---- | ---- |
| 在貼文底下**留言**，出現關鍵字 | 留言自動私訊（本頁） | 私訊留言者一則訊息，可另外公開回覆留言 |
| 在 LINE、Messenger、IG **私訊**中傳關鍵字 | [關鍵字回覆](/dashboard/line/keyword-replies) | 在對話中回覆素材或發券，每次都會回 |
| 其他事件（加好友、建立工單、貼標籤……） | [自動化](/dashboard/automation) | 依規則執行多種動作 |

另外在「關鍵字回覆」頁的說明區塊最後加一行（屬於本 change 的小改動）：
「顧客在 Facebook、Instagram 貼文留言時要自動私訊，請到『留言自動私訊』設定。」

留言自動私訊**不出現在自動化規則列表**，也不能在自動化編輯器編輯（底層是獨立模組，見初步規劃）。避免「關鍵字回覆」那種
「渠道條件請到自動化規則編輯」的雙入口問題。

## 3. 規則列表與編輯

### 3.1 規則列表

沿用關鍵字回覆頁的表格。欄位：

| 欄 | 內容 | 備註 |
| ---- | ---- | ---- |
| 順序 | 數字 1、2、3… 與上移／下移按鈕 | 只有 `manage` 看得到按鈕。不用拖曳（鍵盤與觸控不友善） |
| 狀態 | 「啟用」「停用」pill，可點擊切換 | 同關鍵字回覆頁；停用列 `opacity-50` |
| 規則名稱 | 粗體；名稱下方小字顯示前置條件問題（例如「這個粉專尚未開啟留言接收」`text-warning`） | |
| 渠道 | `ChannelBadge` + 帳號名稱（例如「Facebook · 品牌粉專」） | 一個渠道類型可能有多個粉專，必須顯示帳號名稱 |
| 關鍵字 | chip，最多 5 個，後面「+N」與「（任一／全部）」 | 同關鍵字回覆頁 |
| 貼文範圍 | 「全部貼文」或「3 篇貼文」（hover 顯示貼文摘要） | |
| 私訊內容 | 素材名稱或「文字：前 20 字…」 | 素材停用或刪除時 `text-warning`「素材已停用，不會送出」 |
| 公開回覆 | 「有」「—」 | |
| 近 7 天 | 「送出 128 · 失敗 2」，數字可點，跳到觸發紀錄並帶入篩選 | 讓小編不必切分頁就知道規則有沒有在動 |
| 動作 | 編輯、查看紀錄、刪除 | `view` 只有「查看」「查看紀錄」 |

列表上方：渠道篩選 pill（全部／各粉專與 IG 帳號，只列使用者看得到的），與「建立規則」按鈕。

列表下方固定一行說明：「同一則留言只會套用排在最前面、且命中的那一條規則。每則留言最多私訊一次。」

### 3.2 對話框或獨立頁

**建議用獨立頁**（`/dashboard/comment-replies/new`、`/[ruleId]`），與自動化規則編輯器（`/dashboard/automation/[ruleId]`）一致。理由：

- 欄位比關鍵字回覆多（貼文範圍、公開回覆、同人去重、預覽），對話框需要大量捲動。
- 「從最近貼文挑選」本身是一個有縮圖與搜尋的清單，放在對話框裡會變成對話框疊對話框（焦點管理與 Esc 行為都容易出錯）。
- 獨立頁能放右欄即時預覽（顧客收到的私訊、公開回覆長什麼樣）。
- 觸發紀錄的「規則名稱」與收件匣的系統訊息可以直接連到規則網址。

版面：桌機兩欄（左表單 `lg:col-span-3`、右預覽 `lg:col-span-2` sticky），手機單欄、預覽放在表單下方。
頁尾固定列：「取消」「儲存」；未儲存就離開時跳確認「有尚未儲存的變更，確定離開？」。

### 3.3 欄位規格

依表單由上而下的順序。錯誤訊息顯示在欄位下方（`text-destructive text-xs`），並在頁尾儲存列上方彙總
「有 N 個欄位需要修正」，焦點移到第一個錯誤欄位。

#### (1) 渠道

- 元件：`select`，選項依類型分組：「Facebook 粉專」「Instagram 帳號」，每項顯示帳號名稱。只列使用者有 `full` 存取層級、
  且啟用中的 FB、IG 渠道。
- 預設：列表目前篩選的渠道；沒有篩選且只有一個可選渠道時直接選它；否則空白「請選擇粉專或 IG 帳號」。
- 建立後不能更改（同關鍵字回覆的 design D4），編輯時改成唯讀文字＋說明「渠道建立後不能更改；要換渠道請刪除後重新建立」。
  理由：貼文範圍、素材都綁定渠道，換渠道等於整條規則重做。
- 驗證：必填。錯誤「請選擇粉專或 IG 帳號」。
- 選了之後立即呼叫前置條件檢查（§5），有問題時在欄位下方顯示黃色提示，**不擋儲存**（可以先設好、等重新連結後生效），
  但儲存後列表該列會持續顯示警示。
- 說明文字：「規則只對這一個粉專（或 IG 帳號）的貼文留言生效。」
- 沒有任何可選渠道：整個表單換成空狀態（§5 狀態 A）。

#### (2) 規則名稱

- 元件：`Input`，上限 200 字（同關鍵字回覆）。
- 預設：空白；placeholder「例：雙 11 留 +1 送券、詢問價格」。
- 驗證：必填、去頭尾空白後不得為空。錯誤「請輸入規則名稱」。同渠道重名不擋，只提示「已有同名規則」（`text-warning`）。
- 說明文字：「只給管理用，顧客不會看到」。

#### (3) 關鍵字

- 元件：與 `KeywordReplyEditDialog` 相同的 chip 輸入（Enter 或「加入」）。
- 預設：空。
- 驗證：至少 1 個，最多 20 個；單一關鍵字 1～50 字；重複的不加入（輸入框下方提示「已經加入過了」）。
  錯誤「至少要 1 個關鍵字」。
- 單一字元或純數字（例如「1」）時顯示提示（不擋）：「這個關鍵字很短，留言中只要包含它就會觸發，例如『1』也會命中『100 元』」。
- 說明文字：「比對方式是『包含』且不分大小寫與全形半形。例如關鍵字『+1』也會命中『我要 +1』。」
  （全形半形正規化需要架構確認，見 §11；若不做，拿掉「與全形半形」並建議使用者把「＋1」「+1」都加入。）

#### (4) 比對方式

- 元件：兩個 radio，關鍵字 2 個以上才出現（同關鍵字回覆）。
- 選項：「任一關鍵字出現就觸發」（預設）、「所有關鍵字都要出現才觸發」。
- 不另做「完全相等」：留言常帶表情或贅字，包含比對較符合預期。

#### (5) 貼文範圍

- 元件：兩個 radio。
  - 「全部貼文」（預設）。說明：「包含之後發布的新貼文與廣告貼文的留言」。
  - 「指定貼文」。選了之後展開貼文挑選區（見 3.4）。
- 驗證：選「指定貼文」時至少 1 篇、最多 50 篇。錯誤「請至少選擇 1 篇貼文」。
- 已選貼文以清單顯示：縮圖、內文前 40 字、發布日期、「在 Facebook 開啟」連結、移除按鈕。
  貼文已刪除或讀不到時顯示「讀不到這篇貼文（可能已刪除）」`text-warning`，不自動移除。
- 指定的貼文發布超過 7 天時提示（不擋）：「這篇貼文已發布超過 7 天，之前的留言不會私訊，只有新留言會觸發。」

#### (6) 私訊內容

- 元件：segmented 二選一「素材」「文字」。
  - 素材：`select`，只列這個渠道類型的啟用素材（同關鍵字回覆）。選了之後下方顯示素材摘要卡（名稱、類型、變數提示）。
  - 文字：`textarea`，上限 1,000 字（Messenger 文字上限 2,000 字，保守取一半，留給變數展開），顯示字數。
- 渠道是 Instagram 時：「素材」選項 disabled，說明「Instagram 目前沒有素材，只能用文字」。
- 預設：FB 為「素材」，IG 為「文字」。
- 驗證：
  - 必填。錯誤「請選擇素材或輸入私訊文字」。
  - 素材含顧客專屬券連結時擋下，沿用 `COUPON_URL_IN_RULE_MESSAGE`，並補一句：「留言私訊送出時還沒有顧客資料，
    請改用『回覆關鍵字領券』的玩法」（附關鍵字回覆頁連結）。
  - 素材含變數時提示（不擋）：「留言私訊送出時通常還沒有聯絡人資料，變數會用素材的預設值；沒有預設值則留空。」
  - 素材類型 Meta 不支援用於留言私訊時（由 API 回報，見 §11）：「這個素材的類型不能用於留言私訊，請改選文字、圖片或按鈕範本素材。」
- 說明文字（固定顯示）：「每則留言只能私訊一次，而且要在留言後 7 天內。顧客回覆這則私訊後，對話才會進收件匣。」
- 右欄預覽：以 Messenger／IG 對話泡泡呈現（沿用收件匣 `MessageBubble` 的外觀），標題「顧客會收到」。

#### (7) 同一位留言者只私訊一次

- 元件：switch，預設**開啟**。
- 說明：「開啟時，同一個人在這條規則的範圍內留言多次，只會收到第一次的私訊；後面的留言會記為『已私訊過』。」
- 為什麼預設開：Meta 的限制是「每則留言一次」，不是「每人一次」，熱門活動中同一人連留 5 次就會收到 5 則一樣的私訊，
  很容易被檢舉為垃圾訊息。
- 需要架構支援（依規則＋留言者去重），見 §11。

#### (8) 公開回覆留言（選填）

- 元件：switch「同時公開回覆這則留言」，預設**關閉**；開啟後出現 `textarea`，上限 300 字。
- 驗證：開啟時必填。錯誤「請輸入公開回覆的文字，或關閉公開回覆」。
- 建議支援 1～5 則「輪流使用」的文字（多一個「新增一則」按鈕）：同一段文字在同一篇貼文下重複數百次，會被 Meta 判定為垃圾留言
  而隱藏或限制。第一版若只做一則，說明文字要提醒這個風險。
- 說明文字：「公開回覆會以粉專身分留在貼文底下，所有人都看得到。請不要在這裡放價格或個人資料。私訊沒有送出時，也不會公開回覆。」
- 這一版不做公開回覆時（待決定 2），整個區塊不顯示，不要放 disabled 的空殼。
- 權限未授予（缺 `pages_manage_engagement`）時：switch disabled，說明「需要重新連結 Facebook 並同意『管理貼文互動』權限」＋「重新連結」連結。

#### (9) 啟用

- 元件：頁首右側 switch「啟用」，新建預設**開啟**。
- 存檔成功訊息：「已儲存，規則已啟用」或「已儲存，規則目前停用」（不加勾勾）。

#### (10) 優先順序

- 不在編輯頁出現，在列表用上移／下移調整；新規則排到最後。
- 理由：每則留言只能私訊一次，順序決定「哪一條贏」，在列表中看到相對位置才有意義。

#### 規則試算（輔助工具）

編輯頁底部與列表頁頂端各放一個收合區塊「試試看」：選渠道、（選填）貼上貼文、輸入一段留言文字，按「試算」顯示
「會套用：規則『雙 11 留 +1』」或「不會觸發任何啟用中的規則」。只做比對，不送出任何訊息。對應自動化的「試試看這條規則」。

### 3.4 貼文範圍怎麼選

| 方案 | 做法 | 優點 | 缺點與影響 |
| ---- | ---- | ---- | ---- |
| A. 貼網址或 ID | 文字框貼上，後端解析 | 不用列貼文 | **FB 網址多是 `pfbid…`，不是數字 post ID；IG 網址是 shortcode，不是 media ID**。兩者都無法離線換算，終究要呼叫 Graph API 才能確認，而使用者看不出貼錯沒有 |
| B. 從最近貼文挑 | 後端代呼叫 FB `GET /{page-id}/posts`（或 `published_posts`）、IG `GET /{ig-user-id}/media`，回傳縮圖與摘要 | 小編最熟悉，不會貼錯；能顯示縮圖確認 | 需要新的 API 端點代理 Graph（不存資料庫，可短暫快取）；廣告的未發布貼文（dark post）不在清單內 |
| C. 兩者並存（建議） | 預設 B；清單上方有「貼上貼文網址」輸入框做為補充，後端解析後一樣顯示縮圖確認 | 涵蓋廣告貼文與舊貼文 | 實作量最大 |

**建議 C**，第一版若要縮小，先做 B，A 留第二版。

權限與架構影響（給架構 agent 確認）：

- FB 讀貼文要 `pages_read_engagement`，本功能收 `feed` 留言本來就需要，**不會多要權限**。
- IG 讀 media 要 `instagram_business_basic`（Instagram Login）或 `instagram_basic`，既有私訊串接應已具備，需確認。
- 貼網址：FB 可用 `GET /?id=<url>` 或比對 `permalink_url`；IG 要在最近的 media 清單中比對 `permalink`。找不到時錯誤
  「找不到這篇貼文。請確認是這個粉專（或 IG 帳號）發布的貼文；廣告貼文請貼上廣告預覽網址」。
- 清單分頁：每次 25 筆，「載入更多」；支援以內文關鍵字在已載入的清單中篩選。
- 規則只存 ID（以及顯示用的摘要快照），不在資料庫鏡像貼文。

**IG 與 FB 的差異在 UI 上的呈現**：

| 項目 | Facebook | Instagram |
| ---- | ---- | ---- |
| 欄位名稱 | 貼文 | 貼文（包含 Reels），內部是 media，畫面不出現「media」 |
| 清單縮圖 | 貼文第一張圖，純文字貼文顯示內文 | 一定有圖或影片封面；顯示類型「圖片／輪播／Reels」 |
| 開啟連結 | 「在 Facebook 開啟」 | 「在 Instagram 開啟」 |
| 私訊內容 | 素材或文字 | 只有文字 |
| 留言者顯示 | 名稱 | `@帳號名稱` |
| 不支援 | — | 直播留言（`live_comments`）不觸發，說明區寫明 |

| 欄 | 內容 |
| ---- | ---- |

| 規則 | 規則名稱（連到規則編輯頁）；規則已刪除顯示「（已刪除的規則）」 |

| 結果說明 | 失敗與略過的原因（中文，一行），已送出顯示「顧客已回覆」或「尚未回覆」 |

### 4.2 狀態

| 代碼（建議） | 中文 | 顏色 | 意思 |
| ---- | ---- | ---- | ---- |
| `SENT` | 已送出 | `bg-success-subtle text-success` | 私訊已送出（公開回覆另在詳情顯示） |
| `PENDING` | 處理中 | `bg-primary-subtle text-primary` | 已收到、還在佇列；超過 5 分鐘仍未完成時列表以 `text-warning` 提示「處理時間比平常久」 |
| `FAILED` | 失敗 | `bg-destructive-subtle text-destructive` | Meta 拒絕或系統錯誤，原因見 4.3 |
| `EXPIRED` | 已過期 | `bg-warning-subtle text-warning` | 留言超過 7 天才處理（例如系統暫停、補訂閱後 Meta 補送） |
| `SKIPPED_DUPLICATE` | 已私訊過 | `bg-muted text-muted-foreground` | 「同一位留言者只私訊一次」擋下 |
| `SKIPPED` | 略過 | `bg-muted text-muted-foreground` | 其他不送的原因（規則在處理前被停用、素材停用等），原因寫在結果說明 |

說明：

- 使用者口中的「重複」分兩種，UI 只呈現一種：**Meta 重投同一則留言**由系統直接忽略，不產生第二筆紀錄（使用者不需要知道）；
  **同一個人留很多次**才顯示為「已私訊過」。
- 沒有命中任何規則的留言不記錄（量太大）。紀錄頁空結果時的提示見 4.5。
- 粉專或 IG 帳號自己的留言一律不記錄。

### 4.3 失敗原因對照（API 回代碼，前端對照成中文）

| 原因代碼（建議） | 顯示文字 | 建議動作（顯示在詳情） |
| ---- | ---- | ---- |
| `ALREADY_REPLIED` | 這則留言已經私訊過（可能是在 Meta Business Suite 手動私訊的） | 無需處理 |
| `COMMENT_NOT_FOUND` | 留言已被刪除或隱藏，無法私訊 | 無需處理 |
| `USER_UNAVAILABLE` | 顧客無法接收訊息（可能已封鎖粉專或關閉訊息功能） | 無需處理 |
| `PERMISSION_MISSING` | 粉專授權不足，無法私訊 | 「重新連結 Facebook」按鈕 |
| `TOKEN_EXPIRED` | 粉專連結已失效 | 「重新連結 Facebook」按鈕 |
| `APP_NOT_APPROVED` | 這位顧客不在 App 的測試名單內（App 審核通過前只有測試帳號能收到） | 連到說明（§5 狀態 D） |
| `RATE_LIMITED` | Meta 暫時限制發送次數，系統已重試仍未成功 | 稍後到詳情按「重試」 |
| `MATERIAL_UNAVAILABLE` | 素材已刪除或停用 | 「編輯規則」 |
| `MATERIAL_UNSUPPORTED` | 這個素材的類型不能用於留言私訊 | 「編輯規則」 |
| `UNKNOWN` | 送出失敗（Meta 回應：{原始訊息前 100 字}） | 「重試」；持續發生請洽管理員 |

原始錯誤碼與訊息放在詳情的「技術資訊」收合區（`font-mono text-xs`），給工程師與 Meta 客服用，不放在列表。

「重試」只在原因屬於可重試（`RATE_LIMITED`、`UNKNOWN`、`TOKEN_EXPIRED` 修好後）且留言未滿 7 天時出現；按下後確認
「確定重新私訊這位留言者？Meta 每則留言只允許私訊一次，若先前其實已送達，這次會失敗。」需要 `comment_reply.manage`。

### 4.4 篩選

- 狀態（多選 pill：全部、已送出、失敗、已過期、已私訊過、略過、處理中）

### 4.5 點進去看到什麼

右側抽屜（`Sheet` 樣式，桌機寬 480px，手機全螢幕），內容由上而下：

1. 狀態 pill＋結果說明＋建議動作按鈕（重新連結、編輯規則、重試）
2. **留言**：留言者名稱、留言時間、留言全文（命中關鍵字標示）、「這是對另一則留言的回覆」標記（有 parent 時）、
   「在 Facebook 開啟留言」連結
3. **貼文**：縮圖、內文前 100 字、「在 Facebook 開啟貼文」
4. **私訊內容**：送出的內容預覽（素材以泡泡呈現；記錄當下的快照，規則後來改了也不影響）、送出時間
5. **公開回覆**：文字與狀態（已回覆／失敗與原因／未設定）
6. **後續對話**：
   - 顧客已回覆：「顧客於 11/13 14:20 回覆」＋「到收件匣查看對話」按鈕（需要 `inbox.view` 且看得到該渠道，否則不顯示按鈕，
     只顯示「顧客已回覆」）
   - 尚未回覆：「顧客還沒有回覆。顧客回覆後，對話才會出現在收件匣，24 小時內可以由客服接手。」
7. **規則**：規則名稱連結
8. **技術資訊**（收合）：留言 ID、貼文 ID、Meta 錯誤碼

空結果：

- 有篩選：「沒有符合條件的紀錄」＋「清除篩選」
- 沒有任何紀錄：「還沒有任何留言觸發規則。只有命中啟用中規則的留言會記錄在這裡；沒有命中的留言不會記錄。
  想確認某段留言會不會觸發，可以用上方的『試試看』。」

## 5. 空狀態與前置條件

頁面載入時呼叫前置條件檢查 API（§11），在分頁上方顯示**一張**狀態卡（多個問題時列成清單，最嚴重的放最上面）。
沿用 follow-gift 頁 `rounded-md border px-4 py-3` 的提示卡樣式。

### 狀態 A：沒有任何 FB 或 IG 渠道

整頁空狀態（虛線框，同關鍵字回覆頁的空狀態）：

> **還沒有可以使用的粉專或 IG 帳號**
> 留言自動私訊需要先連結 Facebook 粉專或 Instagram 專業帳號。
> [前往渠道管理]（只有有 `channel.manage` 的人看到按鈕；其他人顯示「請洽管理員連結渠道」）

使用者有渠道但都不在自己的可見範圍：「你目前沒有可使用的粉專或 IG 帳號。若需要使用，請洽管理員開放渠道權限。」
（不要說「沒有渠道」，同 `ChannelManagement.tsx` 對 403 的處理原則。）

### 狀態 B：渠道沒訂閱 `feed`／`comments`（既有連結的粉專）

黃色提示卡（`border-warning/30 bg-warning-subtle text-warning`）：

> **2 個帳號尚未開啟留言接收，留言不會觸發規則**
> - Facebook · 品牌粉專 [開啟留言接收]
> - Instagram · @brand_official [重新連結 Instagram]
> 這些帳號是在留言功能推出前連結的。開啟後，只有之後的新留言會觸發。

- FB：若只差訂閱欄位（權限已足夠），按鈕「開啟留言接收」直接呼叫補訂閱 API，不必重新走 OAuth；
  成功後卡片該列消失並顯示「已開啟品牌粉專的留言接收」。失敗時：「開啟失敗：{原因}。請改用『重新連結 Facebook』。」
- 權限不足時按鈕改為「重新連結 Facebook」，導到既有 Meta 連結流程，完成後回到本頁（帶 `returnTo`）。
- 需要 `channel.manage` 才能按；沒有時顯示「請洽管理員到渠道管理重新連結」。

### 狀態 C：權限不足（使用者拒絕了某個權限）

> **品牌粉專缺少必要的授權**
> 連結 Facebook 時沒有同意「管理粉專貼文互動」與「讀取貼文留言」權限，系統收不到留言也無法私訊。
> [重新連結 Facebook]
> 重新連結時，請在 Facebook 的授權畫面保留所有勾選的項目。

公開回覆所需的權限單獨缺少時，不顯示整頁警告，只在規則編輯頁的公開回覆區塊提示（§3.3 (8)）。

### 狀態 D：App 審核前（只有測試帳號能用）

這是平台層面的狀態（整個 App 還沒拿到 Advanced Access），由 API 回傳旗標，顯示藍色資訊卡（`border-primary-border bg-primary-subtle`）：

> **目前為測試階段**
> Meta 尚未核准本系統的留言私訊權限。核准前，只有在 Meta 開發者後台被加為測試人員的帳號留言時才會收到私訊；
> 一般顧客留言會記為「失敗：不在 App 的測試名單內」。
> 正式上線時間請洽 open333CRM 客服。

- 不放「申請」按鈕（租戶無法自行處理）。
- 這張卡也會出現在規則編輯頁頂端，避免小編以為設好了就能辦活動。

### 狀態 E：方案未包含（若做成方案 feature）

沿用既有 feature 未開通的處理：側欄項目隱藏（`filterTree` 依權限，權限依 feature），直接打網址則顯示
「你目前的方案未包含留言自動私訊。請洽管理員升級方案。」

### 狀態 F：有渠道、沒規則

> **尚未建立任何留言自動私訊規則**
> 顧客在貼文留言出現關鍵字時，系統會自動私訊他一則訊息。
> [建立第一條規則]

## 6. 限制的溝通

目標：使用者在「設定時」就知道限制，而不是在「客訴時」才知道。每個限制只在最相關的位置講一次，加上一處總整理。

| 限制 | 在哪裡講 | 文案 |
| ---- | ---- | ---- |
| 每則留言只能私訊一次 | 規則編輯頁「私訊內容」說明；列表下方固定說明 | 「每則留言只能私訊一次。同一則留言只會套用排在最前面的規則。」 |
| 留言後 7 天內 | 私訊內容說明；指定舊貼文時的提示；紀錄狀態「已過期」 | 「留言超過 7 天就不能再私訊，這類留言會記為『已過期』。」 |
| 24 小時視窗 | 規則編輯頁右欄預覽下方；紀錄詳情「後續對話」 | 「顧客回覆私訊後，24 小時內客服可以在收件匣繼續回覆。顧客沒有回覆前，不能再傳第二則訊息。」 |
| 顧客回覆後才進收件匣 | 頁首「怎麼用？」第 3 點；紀錄詳情 | 「私訊送出後不會立刻出現在收件匣，顧客回覆後才會。」 |
| 私訊可能落在「訊息請求」 | 「怎麼用？」區塊的黃色提醒 | 「沒有和粉專聊過天的顧客，可能會在 Messenger 或 IG 的『訊息請求』裡看到這則私訊。建議在公開回覆中提醒顧客查看。」（需架構查證 Meta 現行行為，見 §11） |
| 編輯過的留言、直播留言不觸發 | 「怎麼用？」區塊 | 「只有新留言會觸發；顧客編輯留言、直播中的留言不會觸發。」 |
| 只有新留言 | 「怎麼用？」與狀態 B | 「規則建立或帳號開啟留言接收之前的留言不會補送。」 |

頁首「怎麼用？」區塊（沿用關鍵字回覆頁的 `ol` 結構）：

1. 先選粉專或 IG 帳號，設定關鍵字與要私訊的內容（FB 可用素材庫的素材，IG 目前只能用文字）。
2. 顧客在貼文留言出現關鍵字 → 系統私訊他一次；有設定時，也會用粉專身分公開回覆這則留言。
3. 顧客回覆私訊後，對話會進收件匣，並標示「來自留言」。私訊送出、失敗或過期，都記在「觸發紀錄」。

黃色提醒（同關鍵字回覆頁的 `bg-warning-subtle` 區塊）：
「每則留言只能私訊一次，且限留言後 7 天內。只有新留言會觸發，編輯過的留言與直播留言不會。沒有和粉專聊過天的顧客，
可能會在『訊息請求』裡看到私訊。」

## 7. 與收件匣的串接

顧客回覆私訊後，照現有私訊流程建立（或延續）對話。UI 上：

1. **對話開頭的系統訊息**（沿用 `MessageBubble` 的 system 樣式），插在顧客第一則回覆之前：
   「此對話來自貼文留言：顧客在〈貼文前 20 字…〉留言『我要 +1』，系統依規則『雙 11 留 +1』自動私訊。
   [查看留言紀錄]」
   - 連結到觸發紀錄詳情（`/dashboard/comment-replies?tab=logs&logId=…`）；沒有 `comment_reply.view` 時不顯示連結，只顯示文字。
2. **私訊本身也要出現在對話裡**：系統送出的那則私訊應補進對話作為第一則外送訊息（發送者顯示「自動私訊」），
   客服才知道顧客在回什麼。若架構上無法補，系統訊息中至少要附私訊內容摘要。
3. **對話列表標記**：`ConversationListItem` 名稱旁加小標籤「來自留言」（`border-border bg-muted text-[11px]`，同關鍵字回覆的渠道 pill），
   只在對話的第一個來源是留言私訊時顯示，7 天後不再顯示（避免永久標籤占空間）——或改為永久顯示，由使用者決定（§10）。
4. **篩選**：`FilterChips` 新增「來自留言」篩選（第二版可做；第一版先有標記即可）。
5. **聯絡人時間軸**：聯絡人詳情的 timeline 新增事件「在 Facebook 貼文留言並收到自動私訊」，連結到紀錄。

## 8. 權限

### 8.1 `comment_reply.view` 與 `comment_reply.manage`

| 畫面元素 | 只有 view | 有 manage |
| ---- | ---- | ---- |
| 側欄入口 | 顯示 | 顯示 |
| 「建立規則」按鈕 | 不顯示 | 顯示 |
| 規則列表狀態 pill | 靜態文字，不可點 | 可點切換 |
| 上移／下移 | 不顯示，只顯示順序數字 | 顯示 |
| 列表動作 | 「查看」「查看紀錄」 | 「編輯」「查看紀錄」「刪除」 |
| 規則頁 | 唯讀模式：所有欄位 disabled，頁首灰色提示「你只有檢視權限，無法修改規則」，頁尾沒有「儲存」 | 可編輯 |
| 紀錄「重試」 | 不顯示 | 顯示（符合可重試條件時） |
| 前置條件卡的「開啟留言接收」「重新連結」 | 另看 `channel.manage` | 另看 `channel.manage` |
| 「試試看」 | 可用（只比對不送出） | 可用 |

- 不顯示的按鈕直接不渲染，不要 disabled 一排灰按鈕（列表會很雜）；唯讀規則頁例外，表單 disabled 才看得出設定內容。
- 建議 `comment_reply.manage` `dependsOn: ['comment_reply.view']`、`implies: ['channel.view']`（比照 `automation.manage`），
  且需要能選素材（素材列表的讀取權限需架構確認）。
- 後端 403 時前端顯示「你沒有權限執行這個動作」並重新載入權限，不顯示原始錯誤。

### 8.2 渠道可見範圍

- 規則列表、渠道篩選、觸發紀錄、渠道下拉，都只包含使用者看得到的渠道（`getAccessibleChannelIds`）；由後端過濾，前端不自行判斷。
- 能不能**修改**某條規則：除了 `comment_reply.manage`，還要對該渠道有 `full` 存取層級（建議；與「改狀態／指派」同級）。
  看得到但層級不足的規則，列表顯示「查看」並在名稱旁顯示提示「你對這個渠道只有檢視權限」。
- 紀錄中的「到收件匣查看對話」另需 `inbox.view`。
- 直接打一條看不到的規則網址：顯示「找不到這條規則」（404 語意，不洩漏存在與否）。

## 10. 對「待決定」的 UX 觀點

### 1. 範圍：FB 與 IG 同時做，還是先做 FB

**建議：同一版上線 FB 與 IG，但 UI 一開始就以「每條規則一個帳號」設計；若時程吃緊，先上 FB，IG 晚一個版本。**

- UX 上兩者的頁面結構完全相同，差異只有「IG 只能用文字」「直播留言不觸發」「@帳號名稱」，設計成本低。
- 情境 2、3 顯示 IG 需求很實際（IG 少數合法主動觸及方式）。
- 若分兩版：第一版渠道下拉只列 FB，**不要**放 disabled 的「Instagram（即將推出）」選項，以免客訴；在「怎麼用？」寫
  「目前支援 Facebook 粉專」。

### 2. 公開回覆這一版是否做

**建議：做，但預設關閉，並支援多則輪流文字；若送審風險高，第一版先不做，整個區塊不顯示。**

- 「已私訊給你囉」的公開回覆是告知顧客去看私訊的主要管道，能降低「訊息請求」漏看與「為什麼沒收到」客訴，價值高。
- 但它是公開內容，出錯（錯字、重複數百次）傷害品牌，所以預設關閉、加輪流文字、加「私訊失敗就不公開回覆」的規則。
- 若 `pages_manage_engagement` 需要送審而拖慢上線，寧可拆第二版，也不要上線一個多數租戶都按不下去的 switch。

### 3. 方案：獨立 feature 或併入自動化；數量上限

**建議：獨立權限點，feature 先掛在既有 `automation`（或 `channels`），不新增 feature；第一版不設數量上限。**

- 使用者心智：它在側欄是獨立頁、規則不出現在自動化列表，所以權限要獨立（`comment_reply.*`）。
- 但方案層面多一個 feature 就多一個平台方案設定欄位與說明成本；它和「關鍵字回覆」同屬自動回覆類，跟著 `automation` 走最好懂。
  若業務要把它當加價賣點，再拆成獨立 feature。
- 上限：Meta 本身已限制每則留言一次、7 天內，濫用空間有限；加上限反而要做「已達上限」狀態、用量顯示、升級引導三套 UI。
  不做上限就不加限制鍵（proposal 的原則）。

### 4. 留言者沒有對應聯絡人時是否建立聯絡人

**建議：留言當下不建立聯絡人；顧客回覆私訊時照既有私訊流程建立，並把該筆留言紀錄關聯到新聯絡人與對話。**

- 只有名稱和留言者 ID 的聯絡人，在聯絡人列表上是一堆「無法聯繫、無法傳訊」的資料，會讓分眾、廣播的人數失真，
  也增加個資保存範圍。
- 觸發紀錄本身已能回答「誰留了言、有沒有送出」，行銷要名單時用紀錄匯出即可（若要匯出，見 §11）。
- 例外：若之後要做「留言者直接發券」，才需要在留言當下建立聯絡人，屆時另行評估。

### 5. Meta App Review 時程與審核前的使用限制

**建議：審核前功能照常開放給租戶設定，但頁面頂端與規則編輯頁固定顯示「目前為測試階段」資訊卡（§5 狀態 D），
失敗原因明確寫「不在 App 的測試名單內」。不建議審核前把整頁藏起來。**

- 藏起來會讓內部 UAT、創造智能自己的示範無法進行。
- 明講限制，小編就不會在審核前辦正式活動；需要一個平台層旗標（App 是否已取得 Advanced Access）讓 UI 決定顯示與否，
  由平台方在 `/admin` 切換，不靠租戶設定。

### 另外需要使用者決定的 UX 問題

- 「來自留言」標記在收件匣永久顯示，還是只在前 7 天顯示（§7）。
- 第一版是否需要觸發紀錄匯出 CSV（行銷要名單時有用；但含留言者名稱，屬個資匯出，需搭配既有審計）。
- 規則是否需要「活動期間」（開始與結束日期）。建議第二版：第一版用「停用」即可，但活動結束忘記停用是常見失誤。

## 11. 給架構 agent 的需求清單

路徑前綴 `/api/v1/comment-replies`（命名由架構決定）。所有清單都由後端依渠道可見性過濾；錯誤一律 `AppError`，
並回可對照中文的 `code`。

### 11.1 規則

| 端點 | 權限 | 用途與欄位 |
| ---- | ---- | ---- |
| `GET /rules?channelId=` | view | 列表。每筆：`id, name, channelId, channel{ id, channelType, displayName, accountId }, keywords[], matchMode, postScope('all'\|'selected'), posts[{ postId, permalink, thumbnailUrl, excerpt, publishedAt, unavailable }], content{ type:'material'\|'text', materialId, materialName, materialStatus, text }, dedupePerCommenter, publicReply{ enabled, texts[] }, isActive, priority, canEdit, stats7d{ sent, failed, expired, duplicate }, warnings[]`。`canEdit` 由後端依 manage 權限＋渠道存取層級算出，前端不自行推算。`warnings` 為代碼陣列（例如 `CHANNEL_NOT_SUBSCRIBED`、`MATERIAL_INACTIVE`、`PUBLIC_REPLY_PERMISSION_MISSING`）。規則數少，不分頁 |
| `GET /rules/:id` | view | 單筆，同上；看不到的渠道回 404 |
| `POST /rules` | manage | 建立；後端驗證同 §3.3（渠道類型 FB/IG、IG 不可選素材、素材不可含顧客券連結、關鍵字數量與長度、指定貼文 1～50 篇、公開回覆文字 1～5 則各 300 字內）。驗證錯誤回 `details.field` 讓前端標到欄位 |
| `PATCH /rules/:id` | manage | 更新（`channelId` 不可改） |
| `PATCH /rules/:id/active` | manage | 切換啟用 |
| `PUT /rules/order` | manage | 傳入同渠道或全部規則的 `id[]` 重新排序（上移／下移後送出整份順序，避免競態） |
| `DELETE /rules/:id` | manage | 刪除；紀錄保留並顯示「（已刪除的規則）」 |
| `POST /rules/test` | view | 試算：`{ channelId, postId?, text }` → `{ matchedRuleId, matchedRuleName, matchedKeywords[] } \| { matched:false }`。只用同一支純函式比對，不送出 |

### 11.2 貼文挑選（代理 Graph API，不存資料庫）

| 端點 | 權限 | 用途 |
| ---- | ---- | ---- |
| `GET /channels/:channelId/posts?cursor=` | manage | 最近貼文 25 筆：`postId, permalink, thumbnailUrl, excerpt, mediaType('text'\|'image'\|'carousel'\|'video'\|'reels'), publishedAt`，`nextCursor`。FB 用 `/{page-id}/published_posts`、IG 用 `/{ig-user-id}/media`。可短暫快取（例如 60 秒）。Graph 失敗時回 `POSTS_UNAVAILABLE` 與原因代碼（權杖失效、權限不足） |
| `POST /channels/:channelId/posts/resolve` | manage | `{ url }` → 同上單筆或 `POST_NOT_FOUND`。FB 處理 `pfbid` 與數字 ID 兩種網址；IG 以 permalink 比對 |

### 11.3 觸發紀錄

| 端點 | 權限 | 用途 |
| ---- | ---- | ---- |
| `GET /logs` | view | 篩選：`status[]`、`channelId`、`ruleId`、`from`、`to`（`z.coerce.date()`，台灣時間切日由前端換算）、`q`（留言者名稱或留言內容）、`cursor`、`limit`（預設 50）。每筆：`id, status, reasonCode, reasonMessage(原始，前 200 字), commentId, commentText, commentCreatedAt, isReplyToComment, commenterName, commenterUsername, post{ postId, permalink, thumbnailUrl, excerpt }, rule{ id, name, deleted }, channel{ id, channelType, displayName }, processedAt, matchedKeywords[], conversationId?, customerRepliedAt?, publicReplyStatus('sent'\|'failed'\|'not_configured'\|'skipped'), retryable` |
| `GET /logs/summary` | view | 同篩選條件下各狀態筆數（摘要列與分頁標籤的失敗數） |
| `GET /logs/:id` | view | 詳情：上列欄位＋`sentContentSnapshot`（送出當下的私訊內容）、`publicReplyText`、`publicReplyReasonCode`、`metaErrorCode`、`metaErrorSubcode`、`commentPermalink` |
| `POST /logs/:id/retry` | manage | 重試；後端再檢查 7 天與可重試條件，不符回 `RETRY_NOT_ALLOWED` |
| `GET /logs/export`（第二版，待決定） | view | CSV |

狀態與原因代碼請採用 §4.2、§4.3 的清單（名稱可調，但要是封閉列舉，前端才能對照中文；未知代碼前端顯示 `UNKNOWN` 文案）。

### 11.4 前置條件

| 端點 | 權限 | 用途 |
| ---- | ---- | ---- |
| `GET /readiness` | view | 回傳：`appAccessLevel('standard'\|'advanced')`（平台層旗標，決定是否顯示「測試階段」）、`channels[{ channelId, channelType, displayName, subscribed:boolean, missingPermissions[], canPrivateReply:boolean, canPublicReply:boolean, tokenStatus, lastCommentEventAt }]`。只列看得到的 FB/IG 渠道 |
| `POST /channels/:channelId/subscribe-comments` | `channel.manage` | 補訂閱 `feed`（FB）；權限不足時回 `REAUTH_REQUIRED`，前端改導重新連結 |
| 既有 Meta 連結流程 | `channel.manage` | 需支援 `returnTo` 參數，完成後回到 `/dashboard/comment-replies` |

`lastCommentEventAt`（該渠道最後一次收到留言事件的時間）強烈建議：前置條件卡可顯示「最後收到留言：3 分鐘前」，
是判斷「訂閱有沒有生效」最直接的訊號，也是客訴排查的第一步。

### 11.5 收件匣串接

- 對話資料需能查到「來源留言紀錄」：`conversation.origin = { type:'comment_private_reply', logId, ruleName, postExcerpt, commentText }`
  或等效欄位，供系統訊息、列表標記使用。
- 私訊送出後，顧客回覆時建立的對話要把那則私訊補成第一則外送訊息（§7 第 2 點），或至少在系統訊息附內容摘要。
- 關聯依據：送出私訊時 Send API 回傳的 `recipient_id`（PSID）；需確認 FB 留言事件的 `from.id` 與 PSID 不同，不能直接用來比對。
- 對話列表 API 回傳 `origin.type`，供「來自留言」標籤與（第二版）篩選。

### 11.6 即時更新

- 觸發紀錄：第一版用 SWR `refreshInterval: 30000`（同 `useAutomation`）。新資料不直接插入表格（避免使用者正在看的列跳動），
  改顯示「有 N 筆新紀錄 [顯示]」提示列；需要 `GET /logs?since=<最新一筆時間>&countOnly=true` 或 summary 支援 `since`。
- 不需要 Socket.IO 即時推播（處理在背景佇列，30 秒延遲可接受）。若之後要做，事件從 worker 走 Path B（Redis pub/sub）。
- 規則列表的 `stats7d`：載入頁面時取得即可，不輪詢。

### 11.7 需要架構查證的 Meta 行為（影響文案）

1. 留言私訊可用的訊息型態（FB：文字、附件、按鈕範本是否都可；IG：是否只有文字）→ 決定素材類型的過濾與 `MATERIAL_UNSUPPORTED`。
2. 私訊是否會落在「訊息請求」資料夾 → 決定 §6 的提醒要不要寫。
3. 廣告貼文留言的 `post_id` 形式，以及能否從貼文清單取得 → 決定 §3.4「全部貼文含廣告貼文」的文案與貼網址的說明。
4. 對「留言的回覆」（有 `parent_id`）是否能私訊 → 第一版預設也比對，若不能則文案寫明只處理第一層留言。
5. Meta 錯誤碼與 §4.3 原因代碼的對照表。
6. 比對時是否做全形半形與大小寫正規化（`＋1` 與 `+1`）→ 影響 §3.3 (3) 說明文字。
