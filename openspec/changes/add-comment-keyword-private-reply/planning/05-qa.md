## 0. 先看結論

1. **至少兩條從真入口打到底的 feature test 是這個功能的骨幹**：(a) 自己算簽章打 `/webhooks/meta`（及 `/webhooks/fb/:id`、
   `/webhooks/threads/:id`）→ 外掛解析 → 分派 → 收件 → 排入佇列 → 執行 job → 攔截的 Graph API 收到 `recipient.comment_id`
   → 紀錄「已送出」→ 聯絡人建立；(b) 顧客回覆私訊的 webhook → 同一位聯絡人 → 對話出現「系統訊息、私訊快照、顧客訊息」三則。
   單元測試 mock 了外掛與 executor，抓不到「層與層接錯」的 bug（記憶：mock 會藏住整合 bug）。
2. **只攔對外 fetch，不 mock 外掛**：比照 `line-system-events.test.ts`，用真的 FB／IG 外掛，`globalThis.fetch` 換成可設定回應的
   假 Graph API，記錄每一次呼叫的網址與 body。這樣才測得到「body 欄位名稱寫錯」「post_id 格式和規則存的不一致」這類問題。
3. **最可能出包的三件事**：補訂閱或重新連結時把 messaging 欄位蓋掉（私訊全斷，影響所有租戶）、FB 貼文 ID 在「挑選清單」與
   「webhook」兩邊格式不一致（指定貼文的規則永遠不命中，而且測試全綠）、同一則留言被私訊兩次（重投、並行、重試、當機）。
4. **Meta 真實行為有 6 項只能在 UAT 實測**（FB `from.id` 是否等於 PSID、「已私訊過」與「超過期限」的錯誤碼、FB 私訊是否進訊息請求、
   FB 廣告貼文留言是否會送、IG 對回覆留言能否私訊、審核前一般使用者的留言會不會送 webhook）。fixture 先用文件與社群經驗，
   標「待實測」，UAT 實測後補正。
5. **情境總數 246 條**（§2）。需要架構定案的點 24 項（§8.1），需要使用者決定的事 12 項（§8.2）。

### 1.2 測試原則（從記憶與 AGENTS 推出來、這個功能特別要守的）

1. **走過入口到改動點的每一層**：每個 feature 情境寫清楚它從哪個入口進（webhook 函式、HTTP 路由、job 執行函式）。只在 flow
   單元測試成立、沒有任何 feature test 走過的分支，列入 §3.3 的「整合缺口」清單，不算完成。
2. **job 執行用 index.ts 同一個組法**：比照 `broadcast-plain-send.test.ts`，feature test 呼叫「佇列註冊時用的同一個 runner 工廠」
   處理 job，不直接呼叫內部函式。另外**一條**測試走真的 outbox relay＋BullMQ＋Redis（佇列名稱、job 名稱、job data 欄位接錯時
   只有這條會紅）。
3. **正向優先、正反成對**：每個驗證規則都要有「合法值存得進去、讀得回來、值不變」的往返案例，再加壞輸入被擋（`TEST-PLAN.md`
   零之 1）。日期欄位（`posts[].publishedAt`）用前端真正送的格式。
4. **失敗要看得見**：每個失敗或略過情境的 THEN 都要包含「紀錄頁（API `GET /logs`）看得到這筆與原因代碼」，不只斷言 log。
5. **測行為不測原始碼**：唯一例外是「Meta 呼叫不在資料庫交易內」這類結構保證，改用行為測試（§2.3 DM-23：Meta 呼叫期間另一條連線
   看得到已提交的「送出中」狀態），仍不行才用原始碼斷言並註明理由。
6. **斷言要指出是哪一道檢查**：403 一律斷言 `error.details.requiredPermission` 或 `details.limitKey`，避免兩道守門給同樣結果
   而讓突變測試照樣通過（AGENTS「When a test passes as soon as you write it」）。
7. **時間可控**：7 天、跨月、限流時段一律注入 `now`；feature test 用 payload 的 `created_time` 造舊留言，不 sleep。

### 1.3 測試環境前提

- `pnpm test:feature` 需要 `app_tenant`、`app_admin` 密碼（AGENTS Environment Gotchas）。
- 新表要進 `scripts/check-tenant-scoping.mjs` 的 `TENANT_MODELS`；`platform-table-grants.test.ts` 會自動檢查新 FORCE RLS 表的 GRANT，
  漏寫會紅（不必另寫）。
- feature test 用的 Redis 是 docker-compose.dev 的 6380；限流與快取鍵加測試租戶前綴，`afterAll` 用 SCAN 刪除，不可 FLUSHDB。

SELECT status, "reasonCode", count(*)
  FROM comment_reply_logs
 WHERE "tenantId" = '<tenantId>' AND "createdAt" > now() - interval '1 hour'
 GROUP BY 1, 2 ORDER BY 3 DESC;

-- 同一則留言只有一筆
SELECT "channelId", "commentId", count(*) FROM comment_reply_logs
 WHERE "tenantId" = '<tenantId>' GROUP BY 1, 2 HAVING count(*) > 1;

-- 留言者 ID 與 PSID 是否相同（R1 實測）
SELECT "commenterId" /* 03：commenterExternalId */, "recipientUid" /* 03：recipientPsid */,
       ("commenterId" = "recipientUid") AS same
  FROM comment_reply_logs WHERE "tenantId" = '<tenantId>' AND status = 'SENT' ORDER BY "createdAt" DESC LIMIT 20;

-- 聯絡人沒有重複：同一個 uid 只對到一位聯絡人
SELECT ci."channelId", ci.uid, count(DISTINCT ci."contactId")
  FROM channel_identities ci
 WHERE ci.uid IN (SELECT "recipientUid" FROM comment_reply_logs WHERE "tenantId" = '<tenantId>' AND "recipientUid" IS NOT NULL)
 GROUP BY 1, 2 HAVING count(DISTINCT ci."contactId") > 1;

-- 對話訊息順序
SELECT "senderType", direction, "createdAt", left(content::text, 40), metadata->>'source'
  FROM messages WHERE "conversationId" = '<conversationId>' ORDER BY "createdAt";

-- 卡住的處理中
SELECT "channelId", "reasonCode", count(*), min("updatedAt")
  FROM comment_reply_logs WHERE status = 'PENDING' GROUP BY 1, 2;

-- 方案與旗標
SELECT slug, 'comment_reply' = ANY(features) AS has_feature, limits FROM plans ORDER BY slug;
SELECT key, value FROM platform_settings WHERE key ILIKE '%comment%';

### 6.1 專節：補訂閱或重新連結把私訊欄位蓋掉

這是唯一會讓**所有租戶私訊全斷**的回歸（`POST subscribed_apps` 是取代，不是附加；04 §3.2、03 R3）。分四層擋：

1. **外掛／service 單元**（`comment-subscription.test.ts`）：假 Graph 記錄 `subscribed_fields`，斷言是**完整集合**（排序後
   `deepEqual`），不是「包含 feed」。突變：只送 `feed`、少送 `message_echoes`，都要紅。
2. **feature**（`meta-connect-comment-fields.test.ts`）：三種入口都要走——(a) 首次連結、(b) 重新連結（已開／未開留言接收）、
   (c) 後台「開啟留言接收」。每一種都斷言完整欄位集合。另加：(d) 重新連結**沒開**留言接收的粉專，結果恰好是 4 個 messaging 欄位
   （確認沒有多訂 `feed` 讓 webhook 量暴增）。
3. **單一來源**：測試直接 import 程式的 `BASE_SUBSCRIBED_FIELDS` 常數**以外**，再寫一份字面清單比對一次，
   避免有人改了常數而測試跟著變（這是少數允許的「釘住常數」斷言，理由寫在測試註解）。
4. **UAT**（§5.2 步驟 1-0、1-1、1-2、1-14）：補訂閱前後各 `GET subscribed_apps` 對照，並立刻傳一則私訊確認。App 層訂閱
   （Dashboard 勾選 `feed`）時，也要截圖前後的欄位清單——04 §1.4 顯示 App 層目前有 18 個欄位，手動操作時誤取消會一樣出事。
