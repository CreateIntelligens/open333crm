# coupon-redemption

顧客端的券夾呈現、券詳情、核銷流程，以及防重複使用與防濫用的保證。

## ADDED Requirements

### Requirement: 顧客可於券夾查看持有的券

顧客 SHALL 能在券夾中依狀態分頁查看自己持有的券。

#### Scenario: 券夾依狀態分流

- **GIVEN** 顧客持有可用、已使用與已過期的券
- **WHEN** 開啟券夾
- **THEN** 三種狀態分別呈現於不同分頁
- **AND** 每張券顯示面額、名稱與到期資訊

#### Scenario: 沒有任何券

- **GIVEN** 顧客尚未領取任何券
- **WHEN** 開啟券夾
- **THEN** 顯示空狀態說明，而非空白畫面

#### Scenario: 即將到期的券主動提示

- **GIVEN** 顧客持有 2 天後到期的券
- **WHEN** 檢視券夾
- **THEN** 該券的狀態為即將到期並帶剩餘天數 2
- **AND** 4 天後到期的券狀態為可使用

#### Scenario: 已過到期時間的券列為已失效

- **GIVEN** 顧客持有到期時間已過、狀態仍為已領取的券
- **WHEN** 檢視券夾
- **THEN** 該券的狀態為已過期，列在已失效分頁

#### Scenario: 活動提前結束的券註明原因

- **GIVEN** 商家提前結束某券，顧客手上未使用的券因此作廢
- **WHEN** 顧客檢視券夾
- **THEN** 該券的狀態為活動已提前結束，列在已失效分頁

#### Scenario: 分頁數量

- **GIVEN** 顧客持有 2 張可使用、1 張已使用、1 張已過期的券
- **WHEN** 開啟券夾
- **THEN** 回應的分頁數量為可使用 2、已使用 1、已失效 1

### Requirement: 未到生效日的券不顯示序號

券尚未生效且券設定開啟「未到生效日不顯示序號」（預設開啟）時，系統 SHALL 隱藏券號並說明原因與生效日期。

#### Scenario: 生效前檢視券詳情

- **GIVEN** 券的生效日尚未到來
- **WHEN** 顧客開啟券詳情
- **THEN** 券號以遮蔽形式呈現
- **AND** 畫面說明將於何時顯示完整券號
- **AND** 使用按鈕呈現為不可用狀態

#### Scenario: 生效後顯示完整券號

- **GIVEN** 券已到生效日
- **WHEN** 顧客開啟券詳情
- **THEN** 顯示完整券號

#### Scenario: 商家關閉生效前遮蔽

- **GIVEN** 券的生效日尚未到來，且券設定關閉「未到生效日不顯示序號」
- **WHEN** 顧客開啟券詳情
- **THEN** 顯示完整券號
- **AND** 使用按鈕仍呈現為不可用狀態

### Requirement: 核銷方式由商家於券層級選擇

系統 SHALL 允許商家為每張券指定核銷方式：店員驗證碼、店員掃碼、或顧客自助。未指定時採店員驗證碼。

#### Scenario: 店員驗證碼核銷

- **GIVEN** 券的核銷方式為店員驗證碼
- **AND** 顧客在券詳情按下使用
- **WHEN** 進入核銷確認畫面
- **THEN** 確認核銷的操作在店員驗證碼輸入完整前維持不可用
- **AND** 畫面提示將手機交給店員操作

#### Scenario: 顧客自助核銷

- **GIVEN** 券的核銷方式為顧客自助
- **WHEN** 顧客在券詳情確認使用
- **THEN** 不需店員參與即可完成核銷
- **AND** 確認操作需持續動作而非單次點擊，以降低誤觸

#### Scenario: 非自助券不得由顧客端核銷

- **GIVEN** 券的核銷方式為店員驗證碼或店員掃碼
- **WHEN** 顧客端嘗試直接發起核銷
- **THEN** 系統拒絕該請求

#### Scenario: 核銷紀錄保留來源資訊

- **GIVEN** 任一方式完成核銷
- **WHEN** 核銷成功
- **THEN** 核銷紀錄保存核銷時間與核銷方式
- **AND** 經店員核銷者另保存店員識別，可用於門市或店員維度分析

### Requirement: 同一張券只能核銷一次

系統 SHALL 確保同一張券不會被重複核銷，於併發情境下亦然。

#### Scenario: 重複核銷同一張券

- **GIVEN** 某張券已完成核銷
- **WHEN** 再次嘗試核銷該券
- **THEN** 系統拒絕並回報此券已使用
- **AND** 回報先前的核銷時間

#### Scenario: 併發核銷

- **GIVEN** 兩個核銷請求幾乎同時針對同一張券
- **WHEN** 兩者皆嘗試核銷
- **THEN** 僅其中一個成功
- **AND** 另一個被告知此券已使用

### Requirement: 核銷台可掃碼或手動輸入券號

店員 SHALL 能以門市帳號登入核銷台，以掃描或手動輸入券號兩種方式查券，確認後才核銷，並在失敗時得知具體原因（詳見 store-redemption）。

#### Scenario: 掃碼核銷成功

- **GIVEN** 店員以門市帳號登入核銷台
- **WHEN** 掃描顧客券上的 QR Code 並確認核銷
- **THEN** 先顯示券的內容與遮罩後的顧客名稱，確認後完成核銷

#### Scenario: 核銷失敗需說明原因

- **GIVEN** 店員輸入券號
- **WHEN** 該券已使用、已過期、尚未生效、不存在，或需在顧客手機上核銷
- **THEN** 系統分別回報對應原因，而非僅回報失敗

### Requirement: 開啟後計時的券於逾時後失效

採用開啟後計時效期模式的券，系統 SHALL 於顧客開啟後開始計時，逾時未核銷即失效。

#### Scenario: 逾時未核銷

- **GIVEN** 券採開啟後計時模式
- **AND** 顧客已開啟該券
- **WHEN** 超過設定時間仍未核銷
- **THEN** 該券轉為失效
- **AND** 顧客端顯示已過期

### Requirement: 發券一律直接歸戶

系統 SHALL 在發券當下把券歸至已知的聯絡人（對話發券、關鍵字、加好友禮、附券廣播、批次發券、傳訊領券），狀態為已領取，不產生領取憑證。顧客開啟票券連結時才做歸戶驗證。領取憑證的換券端點（`POST /fan/coupons/claim`）已移除（design D30）。

#### Scenario: FB 或 IG 對話中發出的券

- **GIVEN** 座席於 FB 或 IG 對話中發券
- **WHEN** 系統發放該券
- **THEN** 券直接歸至該對話的聯絡人，狀態為已領取，不產生領取憑證
- **AND** 顧客開啟票券連結時須先完成歸戶驗證（見「顧客須完成歸戶驗證才能開啟票券夾」）

#### Scenario: 發放渠道已知身分時免領取

- **GIVEN** 發券時已知顧客的聯絡人
- **WHEN** 系統發放該券
- **THEN** 券直接歸至該顧客名下，不需領取步驟

#### Scenario: 發放來源可供成效歸因

- **GIVEN** 券經任一入口發放
- **WHEN** 查詢該券
- **THEN** 可得知發放方式與發放來源名稱

#### Scenario: 領取憑證端點已移除

- **WHEN** 顧客端呼叫 `POST /api/v1/fan/coupons/claim`
- **THEN** 系統回 404

### Requirement: 顧客須完成歸戶驗證才能開啟票券夾

券夾與核銷相關端點 SHALL 只接受由票券連結換得的顧客憑證，且該聯絡人須已完成歸戶驗證、由本人開啟。已歸戶指顧客本人曾以 email 驗證碼完成 One ID 登記，或以 LINE Login 驗證；手機登記沒有簡訊驗證、不算（2026-10-21 code review 決定：手機號碼可被他人冒填），客服在後台填寫的手機或 email 也不算。已歸戶的顧客 SHALL 在驗證過的裝置（帶有效的裝置憑證）開啟；否則以聯絡人原本的 email 驗證碼確認，不能改填其他 email；聯絡人沒有 email 時走 email 登記（design D24）。需要登記時系統一律引導到 email 登記；租戶沒有啟用 email 登記時，無法驗證。

#### Scenario: 未經驗證的存取請求

- **WHEN** 請求沒有帶顧客憑證，或只帶聯絡人識別
- **THEN** 券夾與核銷端點回 401

#### Scenario: 已驗證的裝置開啟票券連結

- **GIVEN** 聯絡人已完成歸戶，顧客的裝置存有這位聯絡人的裝置憑證
- **WHEN** 顧客開啟有效的票券連結，並帶上裝置憑證
- **THEN** 系統回傳顧客憑證，可以讀取自己的券夾
- **AND** 回應附上換新的裝置憑證（效期 180 天）

#### Scenario: 新裝置或轉傳的連結開啟已歸戶顧客的票券

- **GIVEN** 聯絡人已完成歸戶（例如先以 LINE 驗證），email 為 `dan@aicreate360.com`
- **WHEN** 有人在沒有裝置憑證的裝置開啟這位顧客從 Messenger 收到的票券連結
- **THEN** 系統不回傳顧客憑證，回應 `email_code_required`，附上遮蔽後的 email `d***@aicreate360.com` 與渠道類型
- **AND** 回應不提供 email 登記頁網址，驗證碼只能寄到這個既有的 email

#### Scenario: 其他聯絡人或其他租戶的裝置憑證不算

- **WHEN** 開啟已歸戶顧客的票券連結時，只帶其他聯絡人、其他租戶、被竄改的裝置憑證，或顧客憑證
- **THEN** 系統回應 `email_code_required`，不回傳顧客憑證

#### Scenario: 合併前取得的裝置憑證仍有效

- **GIVEN** 顧客在 FB 聯絡人身分時取得裝置憑證，之後 FB 聯絡人被合併到 LINE 聯絡人
- **WHEN** 顧客帶這個裝置憑證開啟 LINE 聯絡人的票券連結
- **THEN** 系統回傳屬於 LINE 聯絡人的顧客憑證

#### Scenario: 以原 email 驗證碼確認身分

- **GIVEN** 開啟票券連結得到 `email_code_required`
- **WHEN** 顧客要求寄送驗證碼，並輸入信中的 6 位數驗證碼
- **THEN** 系統只寄到聯絡人原本的 email，信件主旨不含驗證碼，驗證碼 10 分鐘內有效
- **AND** 驗證碼正確時回傳顧客憑證與裝置憑證，之後在這台裝置開啟不必再驗證

#### Scenario: 驗證碼錯誤與上限

- **WHEN** 顧客輸入錯誤的驗證碼
- **THEN** 系統回報驗證碼錯誤與剩餘次數
- **AND** 同一組驗證碼錯 5 次後作廢，須重新寄送；同一個票券連結 10 分鐘內最多寄 3 次

#### Scenario: 票券連結失效時不寄驗證碼

- **WHEN** 以不存在或過期的票券連結要求寄送或輸入驗證碼
- **THEN** 系統回 410，不寄信，也不透露任何租戶或聯絡人資料

#### Scenario: 沒有 email 的已歸戶顧客走登記

- **GIVEN** 聯絡人只以 LINE 驗證過，沒有 email
- **WHEN** 有人在沒有裝置憑證的裝置開啟這位顧客的票券連結
- **THEN** 系統回應要求驗證並附上 email 登記頁網址（殘留風險見 issue #344）

#### Scenario: LIFF 驗證後記住裝置

- **WHEN** LINE 顧客在 LIFF 以收券帳號的 ID token 驗證通過
- **THEN** 回應附上裝置憑證，票券頁存下後開啟票券時帶上，直接取得顧客憑證

#### Scenario: email 登記完成後記住裝置

- **WHEN** 顧客從票券頁被引導去 email 登記，輸入正確驗證碼並寫入這位聯絡人
- **THEN** 回應附上這位聯絡人的裝置憑證，登記頁存下後回到票券連結，直接取得顧客憑證
- **AND** 回應為 `merge_requires_chat` 等沒有完成歸戶的結果，或手機登記時，不附裝置憑證

#### Scenario: 未歸戶的顧客開啟票券連結

- **GIVEN** 租戶啟用 email 登記，聯絡人沒有完成過登記
- **WHEN** 顧客開啟有效的票券連結
- **THEN** 系統不回傳顧客憑證，回應要求驗證並附上 email 登記頁的網址
- **AND** 登記頁網址帶回到原票券連結的路徑

#### Scenario: 兩種登記都啟用時用 email

- **GIVEN** 租戶同時啟用手機登記與 email 登記，聯絡人沒有完成過登記
- **WHEN** 顧客開啟有效的票券連結
- **THEN** 回應附上 email 登記頁的網址（email 會驗證信箱擁有權，手機沒有簡訊驗證）

#### Scenario: 手機登記不算歸戶驗證

- **GIVEN** 顧客已以手機登記連結送出手機號碼
- **WHEN** 顧客開啟票券連結
- **THEN** 系統仍要求以 email 驗證

#### Scenario: 租戶只啟用手機登記

- **GIVEN** 租戶只啟用手機登記，沒有啟用 email 登記
- **WHEN** 未歸戶的顧客開啟票券連結
- **THEN** 系統回應無法驗證，請顧客聯絡客服，不回傳顧客憑證

#### Scenario: 未驗證顧客重複開啟票券連結

- **GIVEN** 聯絡人沒有完成過登記
- **WHEN** 顧客在 30 分鐘內開啟同一張票券的連結 10 次
- **THEN** 每次都回應要求驗證，附上同一個登記頁網址，不因登記連結的發放上限而失敗

#### Scenario: 客服手動填寫的手機不算歸戶

- **GIVEN** 聯絡人的手機是客服在後台填寫的，顧客本人沒有登記過
- **WHEN** 顧客開啟票券連結
- **THEN** 系統要求驗證

#### Scenario: 租戶沒有啟用任何登記方式

- **GIVEN** 租戶沒有啟用手機登記，也沒有啟用 email 登記
- **WHEN** 未歸戶的顧客開啟票券連結
- **THEN** 系統回應無法驗證，請顧客聯絡客服，不回傳顧客憑證

#### Scenario: 只能存取自己的券

- **GIVEN** 顧客以自己的憑證存取券夾
- **WHEN** 請求另一位顧客的券
- **THEN** 系統回 404

### Requirement: 確認身分的驗證碼綁定票券連結且只能用一次

以原 email 確認身分的驗證碼 SHALL 綁定寄出它的票券連結（連結本身綁定租戶、聯絡人與該張券），與 email 登記的驗證碼分開存放，只能用於開啟這個連結。驗證通過的驗證碼 SHALL 只能使用一次；開啟票券的後續流程失敗時，同一組驗證碼 SHALL 可以再試。寄送不受租戶是否啟用 email 登記影響，只要求聯絡人已歸戶且有 email（design D24）。

#### Scenario: 驗證碼只能用於寄出它的連結

- **GIVEN** 已歸戶的顧客收到兩張券，各有一個票券連結
- **WHEN** 以第一個連結寄出的驗證碼，送到第二個連結確認
- **THEN** 確認失敗，不換發顧客憑證

#### Scenario: 同一組驗證碼同時送出兩次

- **WHEN** 顧客的正確驗證碼同時被送出兩次
- **THEN** 只有一個請求開啟票券，另一個回報驗證碼已失效

#### Scenario: 開啟票券時暫時失敗

- **WHEN** 驗證碼正確，但開啟票券時資料庫暫時無法連線
- **THEN** 回報錯誤，顧客可以用同一組驗證碼再試一次，不必重寄

### Requirement: 歸戶驗證完成時記錄時間

顧客以 email 驗證碼完成 One ID 登記，或以 LINE Login 驗證時，系統 SHALL 在登記後存續的聯絡人上記錄歸戶驗證時間與方式。因登記而合併時，記錄在合併後保留的聯絡人上。手機登記不記錄歸戶驗證。

#### Scenario: email 驗證後記錄

- **WHEN** 顧客以有效的 email 登記連結輸入正確的驗證碼
- **THEN** 該聯絡人的歸戶驗證方式為 email，並有驗證時間

#### Scenario: 手機登記不記錄

- **WHEN** 顧客以有效的手機登記連結送出手機號碼
- **THEN** 聯絡人寫入手機（或依規則合併），但沒有歸戶驗證時間

#### Scenario: 登記觸發合併

- **GIVEN** 同租戶已有另一位聯絡人使用相同 email
- **WHEN** 顧客送出 email 並因此合併
- **THEN** 合併後保留的聯絡人有歸戶驗證時間

### Requirement: 票券連結

系統 SHALL 在發券訊息中附上票券連結。連結帶一組隨機產生的權杖，綁定租戶、聯絡人與該張券，7 天內可重複開啟，過期或不存在時回 410，且不透露任何租戶或聯絡人資料。聯絡人之後被合併時，連結對應到合併後保留的聯絡人。

#### Scenario: 開啟有效連結

- **GIVEN** 已歸戶的顧客收到發券訊息，並在驗證過的裝置開啟
- **WHEN** 顧客在 7 天內第二次開啟同一連結
- **THEN** 系統仍回傳顧客憑證與該張券的識別

#### Scenario: 連結過期

- **WHEN** 顧客在發券 8 天後開啟連結
- **THEN** 系統回 410

#### Scenario: 聯絡人已合併

- **GIVEN** 收到連結的 FB 聯絡人之後因登記被合併到 LINE 聯絡人
- **WHEN** 顧客開啟該連結
- **THEN** 回傳的顧客憑證屬於合併後保留的 LINE 聯絡人

### Requirement: 店員驗證碼核銷須在時限內完成

核銷方式為店員驗證碼時，顧客按下使用後系統 SHALL 開啟 5 分鐘的核銷時段。時段內輸入正確的驗證碼才能核銷；驗證碼錯誤 5 次或時段結束後，時段關閉，須重新按下使用。驗證碼錯誤時不透露正確的碼。

#### Scenario: 時段內輸入正確驗證碼

- **GIVEN** 顧客已按下使用
- **WHEN** 在 5 分鐘內送出正確的驗證碼
- **THEN** 券轉為已使用，核銷方式為店員驗證碼

#### Scenario: 驗證碼錯誤

- **WHEN** 時段內送出錯誤的驗證碼
- **THEN** 系統回報驗證碼錯誤與剩餘次數，券維持可使用

#### Scenario: 錯誤達 5 次

- **WHEN** 同一時段內第 5 次送出錯誤的驗證碼
- **THEN** 時段關閉，之後送出正確的驗證碼也回報須重新開始

#### Scenario: 時段結束

- **GIVEN** 顧客按下使用已超過 5 分鐘
- **WHEN** 送出正確的驗證碼
- **THEN** 系統回報核銷時間已結束，券維持可使用

#### Scenario: 沒有開始就送出驗證碼

- **WHEN** 顧客沒有按下使用就送出驗證碼
- **THEN** 系統回報須先開始使用，券維持可使用

#### Scenario: 一天內錯誤累計達 10 次

- **GIVEN** 同一張券 24 小時內已輸入錯誤的驗證碼 10 次（跨多個時段）
- **WHEN** 顧客按「立即使用」或送出驗證碼
- **THEN** 系統回報 409，錯誤碼為 TOO_MANY_ATTEMPTS，券未被使用；24 小時後才能再核銷

#### Scenario: 同時送出多個驗證碼

- **GIVEN** 核銷時段剛開始
- **WHEN** 同時送出 8 個不同的驗證碼
- **THEN** 最多比對 5 個，其餘回報 SESSION_REQUIRED

### Requirement: 店員掃碼後顧客端得知核銷完成

核銷方式為店員掃碼時，顧客端 SHALL 顯示該券的券號 QR Code，並能查詢到該券已被核銷。

#### Scenario: 店員核銷後查詢

- **GIVEN** 顧客正在出示店員掃碼券的 QR Code
- **WHEN** 店員完成核銷後，顧客端再次查詢該券
- **THEN** 該券狀態為已使用，並帶核銷時間

#### Scenario: 只有可使用的店員掃碼券能取得 QR Code

- **WHEN** 顧客取得可使用的店員掃碼券的 QR Code
- **THEN** 回傳內容為該券券號的 QR Code 圖片
- **WHEN** 顧客取得已使用、未到生效日或不是店員掃碼的券的 QR Code
- **THEN** 系統回 409，不回傳券號

#### Scenario: 驗證碼輸入格數

- **WHEN** 顧客查看店員驗證碼券
- **THEN** 回應帶驗證碼的位數，不帶驗證碼本身

### Requirement: 合併聯絡人時券跟著移到保留方

合併兩位聯絡人時，系統 SHALL 把被合併方的券移到保留方，並在保留方沒有歸戶驗證時帶入被合併方的歸戶驗證。解除合併時，這些券回到原聯絡人，帶入的歸戶驗證也移除。

#### Scenario: 合併後券在保留方的券夾

- **GIVEN** FB 聯絡人持有一張已領取的券
- **WHEN** 該聯絡人被合併到 LINE 聯絡人
- **THEN** 這張券屬於 LINE 聯絡人

#### Scenario: 合併時帶入歸戶驗證

- **GIVEN** 被合併方已歸戶，保留方沒有
- **WHEN** 合併
- **THEN** 保留方有歸戶驗證時間與方式

#### Scenario: 解除合併時券回到原聯絡人

- **GIVEN** 合併時移過去的券
- **WHEN** 解除該次合併
- **THEN** 券回到原 FB 聯絡人，保留方被帶入的歸戶驗證移除

### Requirement: 票券頁依顧客的渠道顯示返回文字

票券連結換取顧客憑證時，系統 SHALL 回傳連結所屬的渠道類型，票券頁的返回按鈕與說明 SHALL 依渠道顯示：LINE 為「回到 LINE」、Facebook 為「回到 Messenger」、Instagram 為「回到 Instagram」，網站客服與無法判斷時為「回到對話」。

#### Scenario: 從 Facebook 開啟票券連結

- **GIVEN** 發券訊息由 Facebook 對話送出
- **WHEN** 顧客開啟票券連結
- **THEN** 回應的渠道類型為 FB，票券頁顯示「回到 Messenger」，不出現「LINE」

#### Scenario: 從網站客服開啟票券連結

- **GIVEN** 發券訊息由網站客服對話送出
- **WHEN** 顧客開啟票券連結
- **THEN** 票券頁顯示「回到對話」

#### Scenario: 連結失效時不知道渠道

- **WHEN** 顧客開啟已失效的票券連結
- **THEN** 說明文字請顧客「回到對話重新點選」，不寫特定渠道

### Requirement: LINE 顧客以 LINE Login 驗證身分

LINE 渠道同時設定 LIFF App ID 與 LINE Login Channel ID 時，系統 SHALL 讓從該渠道收到券的顧客以 LIFF 取得的 ID token 完成歸戶驗證，不必登記 email 或手機。系統 SHALL 以該渠道的 Login Channel ID 向 LINE 驗證 ID token，租戶由票券連結決定，不信任網址參數。ID token 的使用者必須是收到這張券的 LINE 帳號。驗證失敗或渠道沒有設定時，系統 SHALL 改走 One ID 登記。

#### Scenario: LINE 顧客從 LIFF 開啟票券連結

- **GIVEN** LINE 渠道設定了 LIFF App ID 與 Login Channel ID，顧客還沒完成歸戶
- **WHEN** 顧客在 LINE 開啟票券連結，LIFF 送出 LINE 驗證通過、使用者為收券帳號的 ID token
- **THEN** 聯絡人記錄歸戶驗證（方式為 line），回應成功並附上裝置憑證
- **AND** 之後在同一台裝置帶裝置憑證開啟這張票券，直接取得顧客憑證，不要求登記

#### Scenario: ID token 驗證失敗

- **WHEN** ID token 過期、被竄改，或由其他 Login channel 簽發，LINE 驗證不通過
- **THEN** 系統回報驗證失敗，聯絡人不記錄歸戶驗證，頁面改走 One ID 登記

#### Scenario: 用其他 LINE 帳號開啟轉傳的連結

- **WHEN** ID token 驗證通過，但使用者不是收到這張券的 LINE 帳號
- **THEN** 系統回報帳號不符，不記錄歸戶驗證，也不回傳顧客憑證

#### Scenario: 渠道沒有設定 Login Channel ID

- **GIVEN** LINE 渠道只設定 LIFF App ID
- **WHEN** 顧客以 LIFF 送出 ID token
- **THEN** 系統回報未設定，頁面改走 One ID 登記
- **AND** 從這個渠道發出的票券連結維持一般網址

#### Scenario: 設定後發券連結改為 LIFF 網址

- **GIVEN** LINE 渠道設定了 LIFF App ID 1660000000-AbCdEfGh 與 Login Channel ID
- **WHEN** 座席在這個渠道的對話發券
- **THEN** 訊息中的連結為 `https://liff.line.me/1660000000-AbCdEfGh?ct={票券權杖}&lid=1660000000-AbCdEfGh`

#### Scenario: Login Channel ID 格式不對

- **WHEN** 管理者在 LINE 渠道設定填入不是 10 位數字的 Login Channel ID
- **THEN** 系統回報 400，說明 Login Channel ID 為 10 位數字

### Requirement: 從票券頁登記不自動合併帳號

顧客從票券連結被引導去登記時（登記頁網址帶回票券的路徑），送出並驗證的 email 若已屬於同租戶的另一位聯絡人，系統 SHALL NOT 自動合併，也不寫入 email、不記錄歸戶驗證；回應 `merge_requires_chat`，並在收券的對話送出說明，請顧客在自己的對話中輸入登記關鍵字完成整合。沒有其他聯絡人使用這個 email 時照常寫入並記錄驗證。對話中主動取得的登記連結維持原本的自動合併規則。（2026-10-21 code review：票券訊息可能被轉傳，業界做法是開券驗證不合併帳號，合併只在獨立的綁定流程中進行。）

#### Scenario: 票券頁登記的 email 已屬於其他聯絡人

- **GIVEN** 聯絡人 B 已使用 `amy@example.com`，A 收到的票券連結被轉傳出去
- **WHEN** 有人從 A 的票券頁登記 `amy@example.com` 並輸入正確驗證碼
- **THEN** A 不併入 B，A 的 email 不變、沒有歸戶驗證時間，回應為 `merge_requires_chat`
- **AND** A 的對話收到「請在對話中輸入登記關鍵字完成整合」的說明

#### Scenario: 票券頁登記的 email 沒有其他人使用

- **WHEN** 顧客從票券頁登記沒有人使用的 email 並通過驗證
- **THEN** 系統寫入 email 並記錄歸戶驗證，顧客可以開啟票券

#### Scenario: 對話中主動登記仍會自動合併

- **WHEN** 顧客在自己的對話輸入登記關鍵字取得連結，登記已屬於另一位聯絡人的 email 並通過驗證
- **THEN** 依原本規則合併
